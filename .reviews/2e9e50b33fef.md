# Review: Nose as a reusable companion for maintainable software from scratch

- Agent file id: `2e9e50b33fef`
- Date: 2026-09-13
- Scope: repository vs stated goals (not a product-code review)
- Evidence: `.nose/docs/goals.md` (including uncommitted Goal 0), workflow, principles, metric CLI, tests, git history of the removed chat dogfood, current `product/`

**Verdict:** The theory and the agent playbook are unusually coherent. As a *reusable companion that a human plus an arbitrary coding agent can clone and talk through to finished, maintainable software*, success is **possible but not yet likely** — roughly **low-to-moderate (about 30–40%)** on a typical run, higher if the agent is careful and the human stays engaged through Phase 2. The principles and metric can still be useful even when the full companion loop fails.

## What the repo actually is

Two products sharing one tree:

| Layer | Role | Evidence |
|---|---|---|
| Seed (`.nose/` + root `AGENTS.md`) | Methodology: 10 atoms, 5-phase agent workflow, Python scorer `W` | 31 markdown files, ~1.4k LOC of stdlib Python, 5 passing tests |
| Product (`product/`) | Intended to be *this clone’s software*. Currently a Phase 1 self-review of Nose | `status.yaml` phase 1 `in_progress`; `phase-1.md` is a review brief, not a product |

User-facing promise (`README.md`, `AGENTS.md`): clone, open with a coding agent, **talk until the product exists**. The agent drives phases; the human does not pick files, yaml, or scores.

A previous dogfood (in-process LLM chat + TUI, axes-driven `src/chat/`) was deleted in `e4d5f53` so the clone would be blank. That example reached **authorities / slice 0**, not a finished handover. The reusable companion therefore has **no in-tree worked example**.

## How clear are the goals?

`goals.md` is a numbered research backlog, not a product spec.

| # | Claim | Clarity | Status in file |
|---|---|---|---|
| **0** (uncommitted) | Human + AI, AI leads phases, high-quality maintainable software that meets the need | One sentence. No success criteria, no “done”, no non-goals, no target user | New; not marked locked |
| **1** | All atomic, non-overlapping, language/domain/size/age-agnostic maintainability principles | Extremely strong claim, clearly stated | Marked **Locked** |
| **2** | Package of tiered agent/human instructions | Clear as a delivery: five phases, agent drives, `W` gate | Treated as done |
| **3** | One metric on **any Python codebase**; lower = cheaper | Clear, but “any” is not qualified | Defined |
| **4** | Implement that metric | Clear (CLI, stdlib, yaml setup) | Implemented |

**Clarity problems:**

1. **Two missions, one file.** Goals 1–4 are a research program (find atoms → instruct agents → score Python). Goal 0 is the product. README sells Goal 0; `goals.md` still reads as 1–4 with 0 taped on top. “Locked” on 1–4 can look like the companion is finished when Goal 0 is unproven.

2. **Goal 1 overclaims in the same sentence that it is locked.** Completeness, non-overlap, and language/age independence are *design intent*, not demonstrated properties. Locking them freezes a hypothesis.

3. **Goal 3 vs Goal 1.** Language-agnostic principles, Python-only metric, Python-specific grains (`T=15` statements, Sonar cognitive complexity, `match` exhaustiveness). That is a staged narrowing, but `goals.md` does not say so.

4. **Goal 3 vs the scorer.** “Any Python codebase” vs `metric.md`: without `product/axes.yaml`, atoms 1–9 are **undefined**. Nose itself cannot be scored (`missing product registry`). The metric measures a *registry-backed* program, not an arbitrary tree.

5. **README is thinner than the workflow.** A new human sees seven lines. The real contract lives in `.nose/docs/` (dot directory, easy to miss). That is consistent with “agent reads AGENTS.md”, but Goal 0’s user is the human, and they get almost no picture of what they are agreeing to.

6. **Current Phase 1 brief vs Goal 0.** `product/phase-1.md` asks to *review this repository*. The workflow’s Phase 4 assumes `src/` software. Using the companion to produce a review is a category mismatch the seed does not forbid.

## Drift: stated goals vs content

### Aligned (real strengths)

- **Change-axis maintainability is a serious model.** Orient / load / edit / check / mass is a clean split. Extra encodings vs uses, one authority per locked axis, floor vs headline, “scanner found nothing is not proof of \(k=1\)” are all consistently applied from principle files through `metric.md` into Phase 4.
- **Workflow matches Goal 2 on paper.** Orchestrator, artifact lists, context reset, plan lint before code, human-out of Phase 4, rewind table in Phase 5, `human.md` language rules — this is a real playbook, not a slogan.
- **Goal 4 exists and runs.** Fixture scores: headline \(W=0.7833\), floor \(0.6167\), `k=3` on duplicated countries. Five pytest-style tests pass when executed directly.
- **Deleted chat product shows the architecture can be applied.** `providers` vs inferred `protocols`, one module per axis, verifies that read authorities — that is Goal 2/3 working as designed, at least for slice 0.

### Drift and holes

| Goal | Drift |
|---|---|
| **0** Meet the human’s need | Phase 4 is **you only**. Need-meeting is front-loaded into Phase 1–2 recaps. No running-product loop until Phase 5. No eval that agents actually recap, wait, and not gold-plate. |
| **0** High quality maintainable software | `W` gates **registry-shaped** cost. It does not score UX, correctness beyond tagged verifies, API stability, ops, security, migrations, dependency health, or team knowledge. A low \(W\) can still be the wrong product. |
| **0** Reusable companion from scratch | Reuse model is copy `.nose/` + `AGENTS.md`. No packaging, no CI, no golden traces, no compliance checker (parked in current `phase-1.md`). Chat dogfood was removed, so a clone has **no example of finished software**. |
| **1** Cover *everything* impacting maintainability | Unmeasured: comments/docs, naming beyond token-overlap findability, error handling, concurrency, data model evolution, build/CI, third-party churn, performance as a change reason, “who knows this”. Some of these are arguably outside “codebase cost”; Goal 1 does not draw that boundary. |
| **1** No overlap | Degree / locality / strength are three scores on the **same extra-site set** (they say so). Size vs complexity share the enclosing unit. Mixing vs coupling are both “other things in mind”. Mass taxes search that findability also feels. The grouping is honest; “no overlap” is not. |
| **1** Language / age / size agnostic | Principles are written in language-neutral terms; measurement is Python AST. **Brownfield / old projects** have no phase: you would need a registry the workflow only builds for greenfield. Accidental volume’s documented entry-point defaults (`__main__.py`, `pyproject` scripts) are **not implemented** — `volume()` only uses yaml entry points + authorities + verifies. |
| **2** Agent drives; human only talks | Entirely **prompt-normative**. Plan lint is a markdown checklist. Context reset is “if you can… if you cannot, say one line and continue” — that undoes the isolation bet. Nothing stops an agent from writing `src/` in Phase 1 or skipping the hunt. |
| **3** Any Python codebase | Requires agent-authored `axes.yaml` with authorities. Headline extras of Meaning+ need a hunt the scorer cannot do. `W` is only as honest as that hunt. |
| **4** Implement the metric | Thin tests (5 functions, no `pytest` in deps, `unittest` does not collect them). Implementation shortcuts: `_match_subject_is_auth` can yield `True` for any match; class units score complexity 0; fan-out is a static floor. Frequency table in Phase 3 (`1→0.1` … `4→0.75`) is not in `metric.md`’s high/medium/low table (numeric `p` is allowed, so this is doc drift, not a scorer bug). |

### Goal 0 vs the rest (the main structural drift)

Goals 1–4 can be “done” while Goal 0 is false. The file already treats 1–4 as locked/defined/implemented. The companion’s success condition — *a non-software human talks, an AI leads, software appears, it matches the need, it stays cheap to change* — has **no locked definition and no remaining in-repo demonstration**.

## Likelihood of meeting Goal 0

Conditional on a typical coding agent (follows `AGENTS.md` unevenly) and a human who will talk but not run a process.

| Outcome | Likelihood | Why |
|---|---|---|
| Human gets *some* software that resembles the brief | Moderate | Phases 1–2 are a normal product conversation with better-than-average structure. Agents already do this without Nose. |
| Software is *honest* vs Phase 2 (few UX surprises) | Moderate-low | Honesty depends on Phase 2 pictures + waiting for recap. Phase 4 then runs without the human. Drift accumulates until Phase 5 complaint → rewind. |
| Software is *cheap to change* on the ten atoms | Moderate **if** the agent keeps one authority per axis and deletes recopies | The chat slice showed this shape. The `W` gate helps only when hunt + registry are real. Game: skip hunt, keep floor \(k\), claim done. |
| Full loop works *repeatably* as a reusable companion | Low | No enforcement, no eval, no in-tree example, context reset optional, Python-only metric, greenfield-only workflow, Goal 0 untested. |
| Principles help a skilled human/agent even if the loop is skipped | High | Best part of the repo. Reading `principles/README.md` already changes how you split modules. |

**Overall: ~30–40%** that clone-and-talk yields maintainable software that meets the need without a software-literate human steering. Closer to **50–60%** with a diligent agent and a human who actually accepts recaps. The limiting factor is not missing markdown; it is **unverified agent compliance** plus **an unproven need-meeting loop**.

## Highest-impact reasons it may fail

1. **The product is instructions, not a harness.** Goal 2’s entire mechanism is “the agent reads the file.” That is the same failure mode as every `AGENTS.md` in the wild.
2. **`W` cannot see what the hunt does not confirm.** Floor under-counts synonyms; headline needs honesty. The gate can pass a messy tree.
3. **Phase 4 without the human** optimizes for maintainability shape, not “is this what I wanted.” Need-meeting is a Phase 5 rewind, i.e. late.
4. **Registry is the metric’s universe.** Missing axes are invisible. A wrong Phase 3 split (or skipped inferred axis) makes `W` look good while change is expensive.
5. **Greenfield Python only**, while Goal 1 claims all languages and ages. Reuse as a companion for existing or non-Python work is out of scope but not labeled as such in Goal 0.
6. **No remaining dogfood.** The one product that exercised axes → code was deleted. New clones cannot imitate a finished run.

## What already works (do not throw out)

- Ten-atom map and the extra-site vs use distinction
- Artifact-scoped context and one Phase 4 task per context (when actually reset)
- Plan lint: one encode task per locked axis, authorities before uses
- Floor vs headline discipline
- Non-technical human protocol (infer, recap, one question, no yaml)

---

## Practical recommendations (priority)

1. **Write Goal 0 as a product spec** with user, success, non-goals, and what “maintainable” means here (the ten atoms, not all of software quality). Mark 1–4 as *inputs to* 0, not substitutes.
2. **Qualify Goal 1.** Completeness/non-overlap/language-agnostic are hypotheses. Split “conceptual atoms” from “Python measurement”. Name out-of-scope costs.
3. **Qualify Goal 3.** Metric applies to Python trees *with a change-axis registry*, not any codebase. Add a brownfield path or explicitly park it.
4. **Keep one worked example** (the chat slice, or a smaller “todo” product) in-tree or as a recorded run. A companion without a demo is a pamphlet.
5. **Turn the plan lint and `W` gate into something an orchestrator can fail closed** (even a tiny checker: every locked axis has exactly one `encodes` task; CLI exit non-zero if `W` rose without a decision id). Prompt-only gates will be skipped.
6. **Restore entry-point defaults** in `volume()` or delete them from principle 10.
7. **Make tests runnable with stdlib** (or add pytest). Five tests that `unittest` cannot collect understate Goal 4.
8. **Do not use this workflow to produce the review of itself** as the live `product/` unless you park Phase 4. A review is not a `src/` program; mixing that into status.yaml confuses the next cold agent.
